# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an ML research project for **question decomposition + knowledge-graph QA** on NHANES (National Health and Nutrition Examination Survey) data, aimed at interpretable depression diagnosis. Fine-tuned Qwen3-8B-Base decomposes complex questions into atomic sub-questions (labeled `searching` or `aggregation`); `searching` sub-questions are then translated to Cypher via few-shot prompting and executed against a Neo4j knowledge graph.

The project runs two training approaches:
1. **SFT (Supervised Fine-Tuning)** with QLoRA across 5 data experiments (plus the current active `decomp_v1` run, outside that numbering — see `--train_file` below; and progressive **curriculum/staged** runs — see `--stage_files` below)
2. **GRPO (Group Relative Policy Optimization)** reinforcement learning on top of an SFT model. Three independent GRPO runs exist: the original on Exp1 (evaluated as Exp6, 6-component reward), one on `decomp_v1` targeting sampling-temperature stability (3-component reward, `grpo_train.py`'s current target), and a third on `decomp_v1_ood` targeting coverage on out-of-distribution templates (`grpo_train_ood.py`) — see "GRPO Training" and "OOD Generalization Work" below.

Beyond the core `input`→`output` decomposition format, a separate **plan-composition** line of work trains models to also emit a symbolic `<PLAN>` block (bound variables + retrieval steps) alongside the decomposition — see "Plan Composition Pipeline" below.

End-to-end pipeline (training → Cypher → answer) is distinct from training-only commands — see "Cypher / KG Evaluation" and "End-to-End Demo" below.

### SFT Training
```bash
python train.py --exp 1              # single experiment
python train.py --exp 1 2 3 4 5      # all experiments
python train.py --exp 1 --epochs 3 --lr 1e-4 --use_wandb
python train.py --train_file train_dataset.json --output_name decomp_v1   # train on an arbitrary file outside the exp1-5 numbering
python train.py --stage_files curriculum_stage1_atomic.json curriculum_stage2_medium_with_replay.json \
    curriculum_stage3_complex_with_replay.json curriculum_stage4_targeted_with_replay.json \
    --val_file curriculum_validation_mixed.json --output_name plan_composition_curriculum_v1
python train.py --stage_files stage1.json stage2.json --output_name foo --init_adapter nhanes_model/foo/stage1/best_model --start_stage 2
```
`--train_file` (path relative to `data/`, or absolute) trains outside the exp1-5 numbering into `nhanes_model/<output_name>/`; since these files don't ship a matching `shared_val.json`, a validation slice is auto-carved off (`--val_split`, default 5%) and written back to `data/` as `<file>_split_train.json` / `<file>_split_val.json`, unless `--val_file` is given explicitly.

`--stage_files` (`train_curriculum()`) trains the **same** model/LoRA adapter sequentially across multiple data files (e.g. easy→hard), all validated against one shared `--val_file`; unlike `--exp`/`--train_file`, the base model + LoRA are loaded **once** and carried across stages (each stage just gets a fresh `Trainer`/optimizer/schedule sized to that stage's data). Output lands in `nhanes_model/<output_name>/stage{N}/`, with the final stage's `best_model` aliased at `nhanes_model/<output_name>/best_model` so `merge_lora.py --run_name <output_name>` works unmodified. `--stage_epochs` gives per-stage epoch counts (defaults to `--epochs` for every stage). To resume an interrupted curriculum run, pass `--init_adapter <prior stage's best_model>` (loads it as the trainable LoRA instead of initializing fresh) and `--start_stage N` (skips stages already completed). This is how `nhanes_model/plan_composition_curriculum_v1/` (stage1–stage4) was produced.

## Architecture

### Training Pipeline
- **`train.py`** — SFT with QLoRA (4-bit NF4 quantization, LoRA on all linear layers). Uses `transformers.Trainer` directly, no TRL dependency. Masks prompt tokens in labels so only assistant responses contribute to loss. Disables Qwen3's `<think>` tags via `enable_thinking=False`.
- **`grpo_train.py`** — GRPO via `trl.GRPOTrainer`. **Currently implements a decomp_v1-targeted stability run**, not the original Exp1 run described in `nhanes_model/grpo/`'s history: it continues `decomp_v1`'s merged SFT model (never previously RL'd), sampling rollouts at `TEMPERATURE=1.0` to directly target instability found by `compare_grpo_stability.py`'s statistical eval (sub-question count drift, and especially the model not stopping cleanly and looping into a second decomposition attempt under sampling). Reward is `mean(count_accuracy, type_accuracy, clean_stop)` — deliberately just these 3 equal-weighted terms (not the earlier 6-component reward: count/entity/repetition/GPT-semantic/format/type) since clean-stop directly targets the dominant failure mode and the smaller reward drops the OpenAI dependency entirely. Output: `nhanes_model/grpo_decompv1/` (kept separate from the pre-existing `nhanes_model/grpo/` so neither run's artifacts overwrite the other's).
- **`merge_lora.py`** / **`merge_grpo.py`** / **`merge_grpo_decompv1.py`** — Merge LoRA adapters into base model for SGLang-compatible inference.
- **`gen_decomp_v1_temp.py`** / **`eval_decomp_v1.py`** / **`compare_grpo_stability.py`** — The stability analysis that motivated the decomp_v1 GRPO run above: `gen_decomp_v1_temp.py` regenerates decomp_v1's decomposition on `data/test_dataset.json` under real sampling (e.g. `--temperature 0.8`/`1.0`, N samples/question), unlike `run_finetuned_pipeline_eval.py` which always uses greedy decoding; `eval_decomp_v1.py` reuses `evaluate.py`'s exact 3-dimension methodology against decomp_v1's cached greedy generations for a like-for-like comparison with the exp1-6 table; `compare_grpo_stability.py` does a paired before/after statistical comparison (paired t-test + Wilcoxon + Cohen's d/h) between two `gen_decomp_v1_temp.py` samples files (e.g. pre- vs post-GRPO, same questions/temperature/N) across sub-question semantic similarity, count exact-match, and self-consistency.

### Plan Composition Pipeline (added 2026-08-23/24)
A third output format, layered on top of the same decomposition task: the model emits a `<PLAN>...</PLAN><DECOMPOSITION>...</DECOMPOSITION>` pair instead of just the bare `Step N:`/`Sub-question:` text. `<PLAN>` gives a symbolic retrieval plan — a `BINDINGS = {...}` JSON dict of extracted entities plus one `Pn = RETRIEVE(relation=..., arg=$binding, ...)` line per step — meant to ground the decomposition in explicit variables/relations before the free-text sub-questions are generated. Example (`data/plan_composition_train.json`):
```
<PLAN>
BINDINGS = {"patient":56,"model":"naive bayes","ratio":"1:1"}
P1 = RETRIEVE(relation="prediction_correctness", patient=$patient, model=$model, ratio=$ratio)
</PLAN>
<DECOMPOSITION>
Step 1: ...
Sub-question: ...  # Type: searching
</DECOMPOSITION>
```
- Trained via `train.py --train_file`/`--stage_files` like any other run — the format itself has no special training-time handling, it's just what the target text looks like in `data/plan_composition_{train,valid,test}.json` (plus `_augmented` variants). Three model generations exist in `nhanes_model/`: `plan_composition_v1`, `plan_composition_v2` (both plain SFT), and `plan_composition_curriculum_v1` (curriculum-trained via `--stage_files`, stage1–stage4 + a `curriculum_validation_mixed.json` held-out set).
- **`eval_plan_composition.py`** — Evaluates a plan-composition run on `data/plan_composition_test.json`. Reuses `evaluate.py`'s exact 3-dimension methodology (semantic similarity, count accuracy, redundancy) against the `<DECOMPOSITION>` portion only — `parse_output`/`truncate_output` match `Step N:`/`Sub-question:` lines, so `<PLAN>` lines are silently skipped by that machinery, same as any other non-matching text. Additionally checks the `<PLAN>` block itself (new, not covered by `evaluate.py`): whether it's present, and whether its `BINDINGS` line parses as valid JSON.
- **`analyze_subquestion_match.py`** — Finer-grained than `evaluate.py`'s aggregate semantic-similarity mean: re-embeds and re-aligns pred vs. ref sub-questions the same way (reusing `evaluate.py`'s exact Hungarian-matching machinery) but keeps each pair's type labels, reporting (a) **coverage** — % of reference sub-questions with an aligned prediction above threshold (reuses `HIGH_SIM_THRESHOLD=0.85` from `evaluate.py` and `HIT_THRESHOLD=0.90` from `calc_hit_rate.py`), split by `searching`/`aggregation`; (b) **type accuracy** among aligned pairs (robust to pred/ref count mismatches, unlike `evaluate.py`'s positional-index type accuracy); (c) aligned-pair semantic similarity split by type. Writes `subquestion_match_analysis.json` alongside the run's other eval outputs (see `nhanes_model/plan_composition_v2/`, `nhanes_model/plan_composition_curriculum_v1/`).

### OOD Generalization Work (added 2026-08-19/20)

As of 2026-08-27 these files **do** have producers/consumers: the `curriculum_stage*`/`curriculum_oppose_sft`/`curriculum_valid_dataset` files feed the `ood_curriculum_progressive`/`ood_curriculum_baseline` SFT runs, and the `curriculum_test_1{00,20}_gold.json` files feed the "OOD Curriculum Comparison" scripts below (`run_progressive_pipeline_compare*.py`, `eval_subq_coverage.py`, `judge_subq_coverage.py`). ### GraphRAG Ablation (exp1/2/3, added 2026-08-28/29 — not yet committed)
A 3-way ablation isolating how much GraphRAG-style entity/path grounding (`entity_retrieval.py`) helps Cypher generation, independent of the OOD-curriculum SFT-model comparison above. All three scripts share identical decomposition parsing, 12 training-derived few-shot demonstrations, Cypher LLM/decoding settings, sequential per-sample execution, Neo4j execution, and final-answer synthesis prompt — the only intended switches are `USE_GRAPHRAG`/`USE_NEIGHBORHOOD_RESCUE`:
- **`experiment1_baseline_fewshot.py`** — `USE_GRAPHRAG=False`. Static few-shot Cypher only; sees only the current sub-question + prior graph rows, never the original input or GraphRAG grounding.
- **`experiment2_fewshot_graphrag.py`** — `USE_GRAPHRAG=True`, `USE_NEIGHBORHOOD_RESCUE=False`. Adds exact entity/path grounding from `entity_retrieval.py`.
- **`experiment3_fewshot_graphrag_rescue.py`** — both `True`. Adds 1–2 hop neighborhood "rescue" context (`retrieve_neighborhood_rescue()`) when primary grounding is missing/empty/unknown — intended as a strict superset of exp2.

All three take `--files <predictions.json>` (each sample needs `input` + `prediction`, with `output` accepted as a fallback so gold/reference files can be dry-run too), `--sglang`/`--sglang_url` to launch or reuse an SGLang server, and write to `results_<EXPERIMENT_NAME>/`. Run against `ood_data/progressive_decomp_for_experiments.json` (progressive-model decompositions over `ood_data/curriculum_test_120_gold.json`'s questions; producing script undeclared) and scored by **`score_experiments.py`** on the same two axes as `run_progressive_pipeline_compare_v2.py` (graph-info coverage vs pooled `gold_results`, answer cosine vs `gold_answer`), broken out by `seen_80`/`unseen_40` question-template subsets — writes `experiments_score_summary.json` / `experiments_score_per_sample.json`.

**Direction-bug fix (2026-08-28/29):** exp3's `unseen_40` coverage was initially *worse* than exp2's (0.765 vs 0.8024) despite rescue being a strict superset — root cause was `retrieve_neighborhood_rescue()` traversing with undirected `-[*1..2]-` and reporting edges without direction, so the Cypher LLM sometimes copied a rescue-context relation with the direction reversed against the strictly-directed static schema/few-shot demos in the same prompt, silently zeroing that step's results and cascading downstream. Fixed by (1) including `from_labels`/`to_labels` per rescue edge so direction is unambiguous, (2) narrowing the rescue trigger (previously fired on ~90% of `entity_recovered_from_original_input` steps even when primary grounding had already succeeded; now only fires when grounding is genuinely missing, dropping from 52/141 to 6/141 triggered steps). Post-fix: exp3 `unseen_40` coverage 0.765→0.8218 (now correctly beats exp2's 0.8024), exec_rate 96.45%→100%. Current results (`experiments_score_summary.json`) reflect the fix; pre-fix artifacts are kept at `results_exp3_fewshot_graphrag_rescue/before_direction_fix/` and `experiments_score_summary_before_exp3_fix.json` for before/after comparison. **This general failure mode — undirected graph context contradicting a directed schema in the same prompt — is worth checking for in any future GraphRAG-context-injection code before assuming a regression means the underlying idea is bad.**

- **`*_version3.py`** variants (`experiment{1,2,3}_..._version3.py`, run together via `./run_all_version3.sh`) — a stricter rewrite of the same ablation: decomposition source is **`prediction` only** (no `output` fallback — gold/reference fields are never used to construct Cypher or the answer), and an `audit_few_shot_provenance()` check (requires `--train_dataset`, e.g. `ood_data/curriculum_oppose_sft.json`) fails fast unless every one of the 12 few-shot demo questions is verifiably present in the supplied training split — some demo examples were swapped out to satisfy this (e.g. patient 200/random-forest and patient 143/logistic-regression examples replacing ones that weren't attested in training). Scored by `score_experiments_version3.py` into `experiments_score_summary_version3.json`. Notably, version3's `unseen_40` numbers are substantially lower for exp2/exp3 (~0.51 graph_coverage) than the non-version3 run (~0.80–0.82) — not fully root-caused, but `rescore_gold_recall.py` shows `score_against_gold` itself has two false-negative sources (signed vs abs `shap_value`, superset gold vs top-k) that depress these numbers; exp2_version3 and exp3_version3 also score nearly identically (rescue triggered on only 6/141 steps, same low rate as the post-fix non-version3 run), so the two are close by construction here, not by a scoring bug.
- **`resynthesize_answers.py`** — Re-runs only the final-answer synthesis step for exp1/2/3 (non-version3), reusing each experiment's already-executed Cypher/Neo4j steps cached in its output JSON, to cheaply pick up a prompt change (a SHAP sign-convention rule: positive `shap_value` → toward depression, negative → away) without re-deriving identical retrieval results.

### Evaluation Pipeline
- **`evaluate.py`** — Launches an SGLang server for fast inference, then evaluates on 3 dimensions:
  1. **Semantic Similarity** — OpenAI `text-embedding-3-large` embeddings + Hungarian matching alignment
  2. **Sub-question Count Accuracy** — exact match and diff analysis
  3. **Redundancy Detection** — embedding cosine similarity flagging + GPT-4o verification (the only dimension needing GPT-4o, not just embeddings; skippable via `evaluate_experiment(..., skip_redundancy=True)` to cut eval time/cost, used by `eval_plan_composition.py`)
- Also includes output truncation logic to handle model generation artifacts. `truncate_output` handles two distinct artifacts: (1) under sampling (temperature > 0) the model sometimes doesn't stop after a complete decomposition and loops into a second, near-duplicate attempt starting again from `Step 1:` — cut at the first non-monotonic `Step N:` restart so only the first complete answer is scored; (2) a stray token glued directly onto a `# Type:` line with no separator (e.g. `aggregationكُمْ`) — `parse_output`'s regex matches the literal `searching`/`aggregation` keyword, not a greedy `\w+`, so garbage doesn't get captured into the type value. `check_prediction.py` is an ad-hoc script for inspecting these artifacts.

### Cypher / KG Pipeline
- **`few_shot_cypher.py`** — Few-shot English→Cypher translation over each extracted sub-question, then executes against Neo4j and records whether results are non-empty. Can auto-launch SGLang for fast generation. Output lands in `exp{N}_test_predictions_cypher_eval.json` and a reference baseline — currently in `cypher_results_old/` (see "Data Layout"; `cypher_results/` now holds the newer method-comparison outputs instead).
- **`calc_hit_rate.py`** — Two-step funnel over Cypher eval outputs:
  1. **Hit Rate**: ref `searching` sub-Qs matched 1-to-1 by a unique prediction sub-Q (cosine ≥ 0.90, Hungarian assignment, predictions deduplicated first).
  2. **Exec Rate**: among hit prediction sub-Qs, fraction whose Cypher returned non-empty results.
  - **Hit Rate vs `evaluate.py`'s Semantic Similarity** — both use the same `text-embedding-3-large` cosine + Hungarian machinery, but they are *not* the same metric. Semantic Similarity is a *soft continuous average* of aligned-pair cosines over **all** sub-Qs (searching + aggregation, no threshold, no dedup) ≈0.98 — it measures decomposition fidelity. Hit Rate *thresholds* that cosine into hit/miss, restricts to **`searching`** only, dedups predictions, and counts coverage of ref sub-Qs (≈87–90%) — it gates the downstream Cypher exec funnel. This is why Semantic Similarity (~0.98) and Hit Rate (~0.88) differ so much.
  - **Threshold caveat:** `HIT_THRESHOLD = 0.90` in code, but the `README.md` results table was generated at **0.92** ("cosine >= 0.92"). The two will not reconcile — re-run `calc_hit_rate.py` (calls OpenAI embeddings) to regenerate numbers at the current code threshold. Hit-rate results are **not** cached to disk; only Cypher exec stats land in `cypher_results_old/combined_metrics.json`.
- **`connect_neo4j.py`** — Shared Neo4j driver/session helpers. Config via `NEO4J_URI`/`NEO4J_USER`/`NEO4J_PASSWORD`/`NEO4J_DATABASE` env vars (defaults to `bolt://localhost:7687`). `few_shot_cypher.py` reads the same env vars with the same localhost defaults (password `12345678`).

### Cypher-Generation Method Comparison (added 2026-08-17/18)
A second, independent line of Cypher-generation work that compares strategies rather than fine-tuning — driven by the base `Qwen3-8B-Base` via in-context prompting only, no fine-tuning or OpenAI dependency for generation itself:
- **`graph_schema.py`** — Builds a compact "schema card" purely from live Neo4j introspection (`db.schema.nodeTypeProperties()`/`relTypeProperties()`): collapses the 20 per-(algorithm, training-ratio) label variants (`naivebayes_1_1`..`randomforest_1_5`) into one entry, inlines actual distinct values for low-cardinality STRING properties (`ENUM_LIMIT = 15`) since names/types alone led the model to guess plausible-but-wrong values (e.g. `'naivebayes'` instead of the real `'Naive Bayes'`), and annotates relationship-pattern-specific constant properties (e.g. `scope: 'local'` vs `'global'` on otherwise-identical `FEATURE_IMPORTANCE` patterns). Deliberately never emits a bracketed placeholder token — an earlier version did, and the model copied it verbatim into generated Cypher as if it were a real label.
- **`entity_retrieval.py`** — Graph-RAG-style grounding: extracts entities (patient id, biomarkers, algorithm families, training ratios) from a question using vocabulary introspected live from the graph (`build_vocab`), then runs small lookups to pull back concrete matching facts (real property values, real relationship direction) as context before Cypher generation. Targets two failure modes a static schema-only card can't fix: guessed-wrong property values and confused relationship direction on multi-hop patterns. Also resolves **decomposition coreference** — later sub-questions referring back to an earlier step's results (e.g. "those 3 biomarkers") — by threading state across a sample's sub-questions (`has_biomarker_coreference` flag); `run_finetuned_pipeline_eval.py` generates Cypher **sequentially within each sample** (not in parallel across sub-questions) specifically so this cross-step coreference resolution works.
- **`run_cypher_qa_comparison.py`** — Compares two Cypher-generation strategies over `data/test_dataset.json`, both via the local base model: **Method 1 (fewshot)** — the fixed hand-written examples from `few_shot_cypher.py`'s `FEW_SHOT_TEMPLATE`, pattern-matching against the new question. **Method 2 (schema)** — `graph_schema.py`'s schema card + `entity_retrieval.py`'s grounding facts, requiring the model to reason about which labels/relationships/properties apply rather than recall a memorized mapping. Extracts sub-questions from each sample's reference `output`, generates Cypher per method, executes against Neo4j, then synthesizes a final answer from retrieved evidence (also via the local model). Scored on Cypher execution/validity rate; writes predictions + `method_comparison_report.{json,md}` + `schema_card_used.txt` to `cypher_results/`.
- **`run_finetuned_pipeline_eval.py`** — Full pipeline eval combining the fine-tuned decomposition model with both Cypher methods above: (1) `decomp_v1` (not the reference `output`) decomposes each `data/test_dataset.json` `input` — tests real decomposition capability end-to-end; (2) for samples where the model's searching-sub-question count matches the reference (so positional alignment to the gold file is trustworthy), each searching sub-question goes through both Cypher methods via base `Qwen3-8B-Base`, sequentially per sample (see coreference note above); (3) executes and compares returned rows against `test_dataset_gold_cypher_executable_goldresult_aligned.yaml`'s (repo root, not `data/`) `gold_result` via column-name-agnostic value-set containment (different Cypher phrasing can legally return differently-named/ordered columns for the same facts). Writes `finetuned_pipeline_report.{json,md}` + `finetuned_pipeline_samples.json` to `cypher_results/`.
- **`compute_pipeline_significance.py`** — Paired significance testing between Method 1 and Method 2 on `cypher_results/finetuned_pipeline_samples.json`: since both methods run on the *same* decomp_v1-decomposed sub-questions, outcomes are paired — McNemar's exact test for the binary metrics (`exec_success`, `has_results`, `gold_full_match`), paired t-test + Wilcoxon + Cohen's d for the continuous `gold_coverage` metric (mirrors `compare_grpo_stability.py`'s methodology). Writes `finetuned_pipeline_method_significance.json`.
- **`export_pipeline_readable_yaml.py`** — Reformats `finetuned_pipeline_samples.json` into a human-readable YAML (same per-example style as `test_dataset_gold_cypher.yaml`), placing method1/method2 Cypher+results+gold-score directly alongside gold per sub-question instead of three separate hard-to-cross-reference JSON files. Also used against the curriculum pipeline outputs (`--samples cypher_results_curriculum_v1_updated/... --out .../method_comparison_readable.yaml`).
- `cypher_results_old/` holds the pre-2026-08-17 exp-based Cypher eval outputs (`combined_metrics.json`, `exp{1,5,6}_test_predictions_cypher_eval.json`, `reference_baseline.json`) set aside when this comparison work started — `calc_hit_rate.py` and the "Hit Rate vs Semantic Similarity" numbers above were computed against that older layout, not the current `cypher_results/` contents.
- `cypher_results_curriculum_v1/` and `cypher_results_curriculum_v1_updated/` — `run_finetuned_pipeline_eval.py` outputs for the curriculum-trained decomposition model rather than `decomp_v1`. `_updated/` additionally contains snapshot subdirs (`before_coreference_fix/`, `before_graphrag_fix/`, `before_new_graph_schema_rewrite/`, `before_reapplied_fixes/`) preserving the pipeline outputs from before each successive fix to `entity_retrieval.py`/`graph_schema.py` — useful for before/after comparison, not live outputs to overwrite.
- `cypher_results_dev/` — outputs from an ad-hoc smaller run (paired with `data/cypher_dev_subset.json`); not produced by a dedicated script or referenced by one — treat as a manual dev/smoke-test scratch area, not a reproducible pipeline stage.
- `cypher_results_progressive_test100/`, `cypher_results_progressive_test120/` (added 2026-08-27) — `run_progressive_pipeline_compare.py` / `..._v2.py` outputs for `ood_curriculum_progressive` on `ood_data/curriculum_test_1{00,20}_gold.json` (`summary.json`, `per_sample.json`, `progressive_decomp_raw.json`). See "OOD Generalization Work" → "OOD Curriculum Comparison".

### Demo / UI
- **`app.py`** — Gradio UI at `:7860`. Loads the merged SFT model (defaults to `nhanes_model/exp5/merged_model`), runs GPT routing → decomposition → few-shot Cypher → Neo4j → GPT-4o-mini answer synthesis (4 pipeline steps, shown as `Step 0/4`–`Step 3/4` in the status bar). Emits per-session event logs (question submits, accordion expand/collapse, login/logout) as JSONL to `ui_logs/ui_events_YYYYMMDD.jsonl`.

It classifies intent as `knowledge_graph` (proceeds to decomposition, optionally rewriting informal/non-English phrasing into the canonical English question forms the SFT model was trained on — shown to the user as `_Interpreted as_: ...`) or `off_topic` (skips the whole pipeline and returns `direct_answer` immediately, still logged to `qa_log`/counted toward quota). Any router exception falls back to passthrough (treats the question as on-topic, unmodified) rather than blocking the pipeline. `generate_cypher_openai()` is a GPT-4o-mini fallback for Cypher generation (same few-shot template as SGLang) to avoid GPU contention with decomposition, though `run_pipeline` currently wires up `generate_cypher_local` (SGLang).
  - **Auth + quota (added 2026-04):** login-gated UI. Usernames are lowercased on both register and login (`Zhang`/`ZHANG`/`zhang` are one account). SQLite at `./ui_users.db` with two tables: `users(username, password_hash, salt, created_at, question_count)` (pbkdf2-sha256, 200k iters, 16-byte hex salt) and `qa_log(username, ts, question, interpreted_as, decomposition, cypher_rows, final_answer, error, duration_s)`. Per-account quota `QUOTA_LIMIT = 110` (raised from 10 on 2026-09-14) (top of `app.py`); every successful *or* failed submit increments the counter and writes a `qa_log` row. The UI shows a login/register tab set first, swaps to the QA view via `gr.State(current_user)` + `visible` toggles, and displays a badge `{remaining}/{QUOTA_LIMIT} questions remaining` after each run.
  - **Crash-resilient question log:** `log_question_submit()` appends to `ui_logs/questions.jsonl` (username, IP via `X-Forwarded-For`, raw question, model) the instant Submit is clicked — before routing/decomposition/Neo4j/synthesis run — so the question survives even if a downstream call hangs or throws. This is separate from both `qa_log` (SQLite, has the full result) and `ui_events_*.jsonl` (UI interaction events).
  - **Public sharing:** `demo.launch(share=False)` — sharing is via a Cloudflare **named tunnel** (`nhanes-qa`), not gradio.live. `app.py` shells out to `./cloudflared tunnel run nhanes-qa` (config in `~/.cloudflared/`), giving a *static* public URL `https://nhanes-depression-qa.com` that survives restarts. Query with `sqlite3 ui_users.db "SELECT ts, username, question, error FROM qa_log ORDER BY id DESC LIMIT 20"` before reading `ui_events_*.jsonl` (which only covers UI interactions, not pipeline output).

### Process Supervision (start.sh / watchdog.sh)
- **`start.sh`** is a thin launcher: it `nohup`s **`watchdog.sh`** and exits. The watchdog is what actually owns the stack.
- **`watchdog.sh`** restarts the *entire* stack (`python app.py` + `sglang.launch_server` + `cloudflared tunnel`) whenever any of three checks fail: a required process is missing, SGLang `:30000/health` is unhealthy, or Gradio `:7860` is unreachable. ### Gotchas
- **SGLang startup timeout**: `few_shot_cypher.py:launch_sglang_server` polls `/health` up to `max_wait` seconds; loading the 8B merged model on an L4 GPU takes ~50–90s but can exceed the original 300s default on slower disks/GPUs, causing `FATAL: SGLang failed to start`. Currently raised to 900s — do not lower it.
- **SGLang server hangs at 0% GPU utilization under sustained load**: `few_shot_cypher.launch_sglang_server` used to pipe the subprocess's stdout/stderr through `subprocess.PIPE`, but nothing ever drains that pipe while the server is running (only the startup-failure branch reads it) — SGLang logs continuously, the ~64KB OS pipe buffer fills, and the server's own logging calls then block on write, freezing the whole process independent of request concurrency. Fixed by redirecting to a real file (`/tmp/sglang_server_{port}.log`) instead of a `PIPE`; don't reintroduce `subprocess.PIPE` here. `launch_sglang_server` also takes an `extra_args` list (e.g. `["--disable-overlap-schedule", "--watchdog-timeout", "120"]`) to trade the overlap scheduler's speed for a hard crash instead of a silent hang if a batch stalls — the overlap scheduler runs the CPU scheduler and GPU worker concurrently, a known deadlock-prone pattern matching these symptoms. **`evaluate.launch_sglang_server` had the same `subprocess.PIPE` bug until 2026-09-12** (fixed the same way: `/tmp/sglang_server_{port}.log`, plus `max_wait` 300→900s) — it is the launcher used by `evaluate.py`, `eval_plan_composition.py`, `gen_test120_reps.py`, `eval_corrected_test250_subq.py`, etc. Symptom there: every request past a certain point in a run times out (`Read timed out`) with GPU at 0% — on `curriculum_test_250` it hit around sample 190 of the *first* pass, so this was not a "second pass" problem.
- **A "Server ready! (took 1s)" line from `evaluate.launch_sglang_server` means a *previous* server was still alive, not a fast launch** — and the run then silently queries whatever model that old server holds. Seen 2026-09-12: on Lightning Studios `python` can resolve to the `/commands/python` bash wrapper, which runs the interpreter as a child (`"$@"`, not `exec`), so `Popen(["python", "-m", "sglang.launch_server"])` + `terminate()` killed only the wrapper and orphaned the real server (+ its `sglang::scheduler`/`sglang::detokenizer` children); the next model's "launch" then hit the old server's `/health` and ran the baseline pass against the progressive model. Fixed in `evaluate.py`: launch with `sys.executable`, `start_new_session=True` + `os.killpg` on shutdown, and a pre-launch `/get_model_info` probe that **raises** if anything is already listening on the port (callers that want reuse pass `--sglang_url` explicitly). `few_shot_cypher.launch_sglang_server` still launches via the bare `python` string — port the same fix if it starts misbehaving. If you ever see "took 1s" in an eval log, treat that run's outputs as contaminated.
- **"3 reps byte-identical at temperature=0" is deterministic REPLAY, not zero noise** (established 2026-09-13, `cypher_results/determinism_probe.json`, probe script kept in that session's scratchpad). Greedy decoding on this SGLang/L4 stack *does* vary: on one server, 40 real Cypher prompts sent sequentially gave 3/40 different outputs between the first (cold-start) pass and later passes (later passes agree with each other; 16-way concurrent passes after warm-up also agree) — the variation comes from server state (cold-start kernels / CUDA-graph / allocator) rather than batch composition, and the diffs are minor (`ORDER BY` column choice, an extra RETURN column). The test_200 few-shot / GraphRAG / GraphRAG-v2 3-rep runs were each *fresh server → identical prompts in identical order, one at a time*, so every rep replays the same server history and comes out identical — those reps prove reproducibility, not run-to-run variance; all inference there rests on the 200-sample paired tests. The decomposition reps (16 concurrent workers, nondeterministic scheduling) do vary (126–147/200 identical). To make Cypher reps measure real noise, break the shared history: shuffle sample order per rep (seed=rep) or run reps on one warmed server without restart. **Measured 2026-09-13 with `run_test200_shuffled_pass.py --arm fewshot --seed 42`** (same few-shot script, fresh server, only the sample order permuted; output un-shuffled and diffed against rep1; `cypher_results/test200_fewshot_shuf42_vs_rep1.json`, raw pass in `results_exp1_5_baseline_original_input_test200_shuf42/`): 24/289 steps (8.3%) produced different Cypher text (9 RETURN-clause-only, 4 ORDER-BY-only, 1 case-only, 10 other), only 9 steps returned different rows, 1 non-empty flag flipped, and graph_coverage moved by +0.0003 overall (2 samples better, 0 worse, 198 identical) — real greedy noise exists but is ~100× smaller than the between-arm effects (0.04–0.10), so the paired-arm conclusions are safe. `progressive_corrected_decomp_test200_shuf42.json` in `ood_data/` is that permuted input (carries `orig_idx`). A second permuted pass (seed 43, `..._shuf43/`) gave the same picture (22/289 text diffs, 10 row diffs, Δ+0.0001). **`merge_test200_shuffled_reps.py`** then builds **`cypher_results/test200_fewshot_exp1_5_3orders.json`** — the statistically honest 3-rep few-shot file: rep1 = original order, rep2 = seed 42, rep3 = seed 43, all un-shuffled to original idx (top-level `rep_orders` holds each permutation), same record layout as the `_3reps.json` files so `score_test200_arms.py`-style scoring works per rep. Scores (`cypher_results/test200_fewshot_3orders_score.json`): overall 0.7513 / 0.7515 / 0.7514 (mean 0.7514 ± 0.0001), seen 0.9542 ×3, unseen 0.5484 / 0.5489 / 0.5487; Cypher identical across reps on 177–179/200 samples, coverage differs on only 2/200. Use `_3orders.json` (not the replayed `_3reps.json`) whenever rep-to-rep variance is being reported; GraphRAG v2 got the same treatment on 2026-09-13 (`run_test200_graphrag_v2_shuffled.sh`: seeds 42/43, same permutations as few-shot so rep2/rep3 are order-paired across arms; `results_exp2_fewshot_graphrag_v2_test200_shuf{42,43}/`) → **`cypher_results/test200_graphrag_v2_exp2_3orders.json`** (slimmed: `records` de-duplicated, `rows_distinct` added). GraphRAG **v1 was dropped** from this line per the user (its only reps are replays). Cross-rep summary (`cypher_results/test200_3orders_score.json`): few-shot 0.7514 ± 0.0001 overall, GraphRAG v2 0.8489 ± 0.0006 (seen 0.9575 ± 0.0029, unseen 0.7402 ± 0.0040; v2 varies a bit more between orders — 34/28 changed steps vs few-shot's 24/22, Cypher identical across reps on 169–174/200 samples); rep-averaged paired v2 − few-shot = +0.0975 overall [+0.063, +0.134], Wilcoxon p≈1e-6 (per-rep p 8e-7…2e-6), d=0.38; unseen +0.192, d=0.58; seen +0.003 n.s. — identical conclusions to the replayed reps, now with honest rep variance.
- **Empty predictions from SGLang timeouts silently poison metrics**: `gen_test120_reps.py` originally kept one server up for rep2 and rep3, and the second pass degraded from ~275s to 700–870s for the same 120 requests until requests exceeded `evaluate.SGLANG_TIMEOUT=60s` — in hindsight this was the `evaluate.py` PIPE-buffer freeze above (more cumulative log output → pipe fills), not server reuse per se, but a fresh server per pass remains the safe default. `run_inference_sglang_batch` then returns `""` for timed-out samples, which scores as "nothing covered, nothing hallucinated" (empty prediction → zero-denominator hallucination rate reads as a perfect 0%) and silently poisons the metrics. Launch a fresh server per pass and raise the per-request timeout (`--timeout 300` there); check any suspiciously perfect metric for empty predictions first.
- `main.py` is a Lightning Studios hello-world stub; ignore it. `draw_url.py` is an unrelated coding exercise (decode a "secret message" grid from a published Google Doc) — not part of this project's pipeline either.

### Question Taxonomy
- `question_templates.md` (Chinese) / `question_templates_en.md` (English) classify the 100 `shared_test.json` complex questions into **11 skeleton templates** (7 pure-lookup + 4 comparison/aggregation), built from a fixed vocabulary of **14 sub-question semantic categories (8 `searching` + 6 `aggregation`)**. These categories are the implicit target of GRPO's type-matching reward and `evaluate.py`'s type-accuracy metric — consult them before changing reward weights, eval logic, or training data balance.
